Recommended Matters design

A + D combined. The sidebar tree from A (matters expand inline) plus the auto-grouping + upgrade flow from D (no setup, "Make this a Matter →" promotes a group to a named matter). Click the Matters label in the sidebar to open the matters index in the main canvas — all matters as cards, grouped by Active / Closed.

How the three pieces fit

From AThe sidebar has a Matters group with each matter as a nested clickable node. Clicking a matter opens it in the main canvas.

From AFrom DThe "Matters" parent label is itself clickable. Click it → opens a Matters index page in the main canvas: every matter as a card, grouped by Active / Closed, with parties, deadlines, letter counts. Same pattern as clicking "Inbox" in Gmail.

From DHome stays auto-grouped by Employer (employee mode) or Person (HR mode). Each group has a "Make this a Matter →" action that promotes it: gives it a name, status, optional deadline; from then on the group lives in the sidebar tree.

  • Users with simple needs (1–2 cases) never have to use the Matter concept — auto-groups work fine.
  • Users with explicit cases get the structure they need without inventing it from scratch.
  • Both populations live in the same app surface — the tree is just empty for the first set.

1 · Clicked "Matters" → index page in main canvas

User clicks the Matters parent label in the sidebar (not a specific matter — the label itself). Main canvas opens to the matters index: every matter as a card, grouped by status, with parties, letter counts, deadlines visible at a glance. Click any card to open that matter (state 2). Cards in the canvas mirror the tree in the sidebar — they're two views of the same data.

What this gives you A single mental model that scales from "I just started; no concept needed" (state 3) to "I run 30 concurrent cases; show me the index" (state 1). Sidebar always reflects what's in the matter set. Auto-grouping does the "obvious" thing on day one; explicit Matters give you the named-case-with-deadline structure when you need it. The transition between the two is a single chip click — no migration, no re-import, no data loss.

Build order: state 3 first (one day) → states 1+2 second (two days, since they share data + most of the components). Both halves run in parallel during week 2.
